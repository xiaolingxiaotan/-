# M6-4 瓶颈分析

## 一、怎么从数据里看出瓶颈

不要猜，看**三级的平均耗时**：

```
[triple] 段均值 {'pre': 3.73, 'infer': 6.30, 'post': 0.88}  (ms)
```

流水线的吞吐上限 = `1 / max(三级)` = `1 / 6.30ms` = **158.7 FPS**。
实测 157.54 FPS，**达到理论上限的 99.3%**——说明流水线本身没有浪费，
剩下的唯一瓶颈就是推理这一级。

反过来，串行的上限是 `1 / (3.73+6.30+0.88)` = `1/10.91ms` = 91.7 FPS。
实测 86.87 FPS。两相对比：

| 方案 | 理论 | 实测 | 达成率 |
| :-- | :-- | :-- | :-- |
| serial | 91.7 FPS | 86.87 FPS | 94.7% |
| triple | 158.7 FPS | 157.54 FPS | 99.3% |

**串行只有 94.7% 达成率，三线程 99.3%** —— 因为串行时每一帧的「取帧 + 统计」
等 Python 开销无法与计算重叠，而三线程里这些开销被藏在别的线程后面。

## 二、为什么 dual 只有 1.10×

双线程结构是 `pre | (infer+post)`，两级耗时：
`pre = 3.73`、`infer+post = 7.18`，理论上限 `1/7.18 = 139 FPS`。
如果它跑满理论值，加速比应该是 139/91.7 = **1.52×**。

实测只有 95.82 FPS，**低于它自己的理论上限 45 FPS**。原因是：

1. **pre 与 infer 争同一批 CPU 核**。letterbox 是 CPU 密集（`cv2.resize` +
   三次 `np.divide`），而 GPU 推理虽然算在 GPU 上，kernel launch、显存
   H2D 拷贝也要占 CPU。
2. 两者挤在一起后，infer 段从 7.83 ms 涨到 **9.93 ms**（实测段均值），
   吞吐自然塌下来。

这解释了题面的追问「为什么双线程通常低于 2×」：**不是「最慢一级 + 后处理串行」
这么简单，而是两个阶段抢同一份 CPU 资源**。三级的好处正是把「抢资源」这件事
摊到三个核上（虽然 Python 有 GIL，但 cv2/numpy/ORT 都会释放 GIL）。

## 三、如果推理只要 5 ms，流水线还有意义吗

有，但**瓶颈会转移到预处理**。本项目就是接近这种情况（infer 6.3 ms），
所以预处理 3.73 ms 已经占到串行耗时的 34%，是第二瓶颈。

极端假设：推理降到 1 ms。那么串行 = 3.73+1+0.88 = 5.61 ms（178 FPS），
三线程 = 1/3.73 = 268 FPS，加速比 1.5× —— **收益反而比现在小**，
而且此时再优化推理毫无意义，该去优化 letterbox（比如用硬件缩放、
或用 `cv2.INTER_NEAREST` + 固定尺寸输入）。

这就是题面那句「瓶颈转移到别处」的实际含义：**流水线的加速比取决于三级是否均衡**。
三级越均衡，加速比越接近 3；严重失衡时（本例 infer 占 58%），上限就只有 1.8×。

## 四、延迟与吞吐的取舍（必须一起报的数）

| 方案 | FPS | P50 延迟 | P95 延迟 |
| :-- | :-- | :-- | :-- |
| serial | 86.87 | 9.56 ms | 19.52 ms |
| dual | 95.82 | 52.54 ms | 111.64 ms |
| triple | **157.54** | 34.57 ms | 60.79 ms |

三线程吞吐是串行的 1.81 倍，但 **P95 延迟是串行的 3.1 倍**。
原因是帧在三个队列里排队：延迟 = 三级耗时 + 排队时间，队列越深排得越久。

所以「只报 FPS 不报延迟」是没有意义的（题面 §5 也这么禁）。
实际选型：

* **导航/避障这类实时闭环** → 用串行或双线程，要的是低延迟；
* **离线分析、录像回放** → 用三线程，要的是吞吐。

本项目现场演示用三线程（看的是 FPS 与流畅度），
但在 M2-4 的追踪里必须用**串行**——因为追踪依赖帧序与低延迟，
排队会引入额外的位置滞后，卡尔曼的预测会偏。
