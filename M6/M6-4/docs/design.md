# M6-4 架构设计与实现

## 一、总体结构

```
[帧源]  (视频/摄像头，每帧由 cap.read() 新分配)
   │  帧引用（不拷贝）
   ▼
┌─────────────────┐  q_pre  ┌──────────────┐  q_post  ┌────────────────────┐
│ 线程A: Preprocess│ ──────> │ 线程B: Infer │ ───────> │ 线程C: Postprocess │
│ letterbox→画布   │ maxsize │ session.run  │ maxsize  │ 解码+NMS+绘制       │
│ 3×np.divide→张量 │   =8    │ (锁保护)      │   =8     │ 归还缓冲 + 发布      │
└─────────────────┘         └──────────────┘          └────────────────────┘
        ▲                                                      │
        └──────────── 缓冲池（6 组，索引传递） ◄────────────────┘
```

## 二、为什么这样分三级

三级的耗时量级差得很远（实测，GPU 模式、600 帧平均）：

| 阶段 | 平均耗时 | 占比 |
| :-- | :-- | :-- |
| 预处理 | 3.73 ms | 34% |
| 推理 | 6.30 ms | 58% |
| 后处理 | 0.88 ms | 8% |
| **串行合计** | **10.91 ms** | 100% |

串行时吞吐受**总和**限制（91.7 FPS），流水线后受**最慢一级**限制
（6.30 ms → 158.7 FPS），这就是加速的来源。

## 三、队列：有界 + 阻塞 = 背压

| 设计 | 选择 | 为什么 |
| :-- | :-- | :-- |
| 容量 | 8（题面示例 4） | 4 在 GPU 模式下会让预处理端频繁等队列；8 实测更稳。容量与延迟成正比：容量越大，帧在队里排队越久，P95 越高（见下方实测） |
| 满了怎么办 | **阻塞等待** | 比赛场景下丢帧 = 漏检一个目标，宁可延迟高也不能丢。丢帧还会让「帧号 ↔ 结果」错位，追踪（M2-4）直接崩 |
| 空了怎么办 | `get(timeout=0.2)` 轮询 | 无限 `get()` 会吞掉 stop 信号，线程 join 不上 |

**maxsize 的权衡**（实测同一输入源）：

| maxsize | 吞吐 | P95 延迟 | 说明 |
| :-- | :-- | :-- | :-- |
| 1 | 接近最慢一级 | 最低 | 几乎没有缓冲，最省内存 |
| 4~8 | 接近上限 | 中等 | 推荐区 |
| 16 | 不再提升 | 明显变高 | 队列只是「堆帧」，吞吐由最慢一级决定 |

## 四、退出与异常

```
任何一级抛异常
    -> _fail(exc)：记录首个异常 + stop.set()
    -> 其余线程在 while not stop.is_set() / get(timeout) / put(timeout) 处退出
    -> 主线程 join(timeout=30) 后把异常重新抛出
```

三条硬约束：

1. **不用 daemon 强杀**（题面 §5 禁止）——强杀会留下半初始化的 session 和未归还的缓冲。
2. **put/acquire 全部带超时**——`q.put()` 在队列满时会无限阻塞，即使 stop 已置位。
   这是本实现里真实踩到的死锁：下游线程死了、队列满，生产者永远卡在 put 上。
3. **join 带 30 秒兜底**——万一还有线程活着，主线程不会一起卡死，而是抛
   `线程未能在 30 秒内退出`。

## 五、三种模式只改「谁在哪个线程里跑」

| 模式 | 线程 | 理论吞吐 |
| :-- | :-- | :-- |
| serial | 1（主线程） | 1/(pre+infer+post) |
| dual | 2（pre / infer+post） | 1/max(pre, infer+post) |
| triple | 3（pre / infer / post） | 1/max(pre, infer, post) |

阶段函数是**同一份代码**，所以三种模式的结果逐帧一致（单测 `test_correctness.py` 验证）。

## 六、实测结果（600 帧，GPU 模式，queue=8）

| 方案 | FPS | P50 | P95 | 加速比 |
| :-- | :-- | :-- | :-- | :-- |
| serial | 86.87 | 9.56 ms | 19.52 ms | 1.00× |
| dual | 95.82 | 52.54 ms | 111.64 ms | 1.10× |
| **triple** | **157.54** | 34.57 ms | 60.79 ms | **1.81×** |

理论天花板 = 1/(6.30ms) = 158.7 FPS，实测 157.54 FPS，**达到 99.3%**。

**为什么 dual 只有 1.10×**：双线程合并了 infer+post，两级变成
`pre=3.73` 与 `infer+post=7.18`，理论 1/(7.18ms)=139 FPS；
但实测只有 95.82 FPS——因为 pre 与 infer 争同一个 CPU（letterbox 是 CPU 密集，
GPU 推理也要 CPU 发指令），GIL 之外的资源竞争把 infer 推高到 9.93 ms。

**为什么 triple 的延迟反而更高**（P50 34.57 ms vs 串行 9.56 ms）：
流水线用**延迟换吞吐**。帧在三个队列间排队，端到端延迟 = 三级耗时 + 排队时间。
要低延迟就用串行，要高吞吐就用三线程——这是不可兼得的取舍，题面要求两个数都报，
就是为了让人看见这个权衡。
