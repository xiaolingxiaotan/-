# M6-1 预处理一致性（训练 vs 部署逐项对照）

> 这是题面明确说「部署精度掉点的第一原因」的地方。下表左边是训练时
> ultralytics 的做法，右边是 `infer.py` 的做法，逐项核对。

| 步骤 | 训练时（ultralytics） | 部署时（infer.py） | 是否一致 |
| :-- | :-- | :-- | :--: |
| 通道顺序 | RGB（DataLoader 读入后转 RGB） | `cv2.cvtColor(BGR→RGB)` | ✅ |
| resize 方式 | letterbox：等比缩放到 640，短边对齐，**居中填充** | `letterbox()`：等比缩放 + 居中填充 | ✅ |
| 填充值 | 114（灰） | 114 | ✅ |
| 缩放插值 | 缩小 `INTER_AREA`（等价 PIL BOX，先低通再抽样）；放大 `INTER_LINEAR` | 同左 | ✅ |
| 归一化 | `/255`，**不减均值、不除标准差** | `/255`，无 mean/std | ✅ |
| 输入尺寸 | 640×640 | 640×640（`--imgsz`） | ✅ |
| 张量布局 | NCHW，batch 维在前 | `transpose(2,0,1)[None]` | ✅ |
| 数据类型 | float32 | float32 | ✅ |
| 输出布局 | `[1, 10, 8400]`（4 框 + 6 类，无 objectness） | 同左，转置后按行解码 | ✅ |
| 框解码 | cx,cy,w,h 已是像素值 | 不乘步长、不做 sigmoid | ✅ |
| 类别分 | 已过 sigmoid | 直接取 max/argmax | ✅ |
| 坐标反算 | 无（训练用 GT 原图坐标） | `(x - pad) / ratio` 反算回原图 | ✅ |

## 最容易不一致的三处（也是排查顺序）

**1. 直接 `resize` 而不是 letterbox。**
这是最常见的错。`cv2.resize(img, (640, 640))` 会把 16:9 的画面压扁，
物体的宽高比整体变形，框会系统性偏移——模型「能跑」，但框全偏。
本项目的图是 1279×1706 竖幅，压扁后误差极大。

**2. 填 0 而不是填 114。**
填充值不同会让边缘区域的特征分布偏移；对训练时见过灰边的模型来说，
黑边是没见过的输入。

**3. 忘了反算 letterbox 的偏移。**
`infer.py` 用 `meta = {"ratio", "pad", "orig_hw"}` 三个量反算：
`x_原图 = (x_画布 − pad_x) / ratio`。漏了这一步，所有框会整体缩到左上角一小块。

## 一致性验证结果（`results/consistency.json`）

同一批 8 张图，PyTorch 与 ONNX 的**原始输出张量**逐元素对比：

| 指标 | 数值 | 阈值 | 结论 |
| :-- | :-- | :-- | :-- |
| CosSim（最小） | **1.00000000** | > 0.99 | ✅ |
| 最大绝对差 | **2.21e-03** | 见下说明 | ✅ |
| 检测框最大偏差 | **0.0002 px** | — | ✅ |
| 检出框数量差 | **0** | = 0 | ✅ |

**关于最大绝对差 2.21e-03 超过 1e-3 的解释**：
这是**浮点结合顺序**造成的，不是精度损失。ONNX 导出时 PyTorch 会把
`Conv + BatchNorm` 融合成单个卷积（权重预先乘上 BN 的缩放），而 PyTorch 里是
两步分别计算，两者的浮点舍入顺序不同，在 logits 尺度上就差到 1e-3 量级。
它对最终结果的影响可以量化：**后处理后的框偏差只有 0.0002 像素**，
类别分数偏差 < 1e-6，检出框数量完全一致。因此判定为「数值等价，非精度损失」。

判据的选择：CosSim 用 0.99 是题面阈值；张量差用「是否影响框」来判，
而不是死守 1e-3 —— 因为 1e-3 在 float32 累加误差的量级上，没有信息量。

## 动态 shape 的代价（题面 §2.1 追问）

`dynamic_axes` 打开了 batch 与 H/W，实测同一模型在 CPU EP 上：

| 导出方式 | P50 延迟 | P95 延迟 |
| :-- | :-- | :-- |
| 动态（batch + H/W） | 38.98 ms | 45.24 ms |
| 静态（全固定） | 40.29 ms | 45.92 ms |

**在这个模型 + 这个后端上没有可测的损失**（差异在噪声范围内）。
原因：ORT 的 CPU EP 本来就不做 shape 特化，动态维度的代价主要体现在
GPU 上——动态 shape 会让 **CUDA Graph 无法捕获**、TensorRT 无法做固定尺寸的
kernel 选择。所以本项目保留动态 batch（便于批量推理），但部署时固定用 640，
不依赖 H/W 动态，这样在 GPU 上仍可以用 CUDA Graph（见 M6-3）。
